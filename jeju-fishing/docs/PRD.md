# 제주 낚시 조황 모아보기 모바일 웹 PRD

- 버전: v0.1
- 작성일: 2026-10-23 (Asia/Seoul)
- 상태: 초안 — 사용자 검토 및 실제 BAND API 연동 검증 전
- 가칭: 제주 조황 모아보기
- 초기 데이터 출처: 네이버 밴드(BAND)
- 문서 목적: 제주 낚시배의 조황을 한눈에 비교하는 모바일 웹의 MVP 요구사항 정의
- 작성 기준: 대화에서 확인된 사용자 요구와 공식 API 문서. 아래의 ‘추천 기본값’은 사용자가 최종 확정한 조건과 구분한다.

## 1. 제품 개요

제주 낚시배가 각자 운영하는 밴드에 게시한 조황을 어종, 낚시 방식, 실제 출조일, 출항 항구, 선박별로 모아 보여주는 모바일 웹이다. 이용자는 여러 밴드를 오가며 글을 찾는 수고를 줄이고, 관심 있는 조황에서 해당 선사의 원문·연락처·예약 채널로 이동할 수 있다.

핵심 사용자 질문은 ‘최근 제주에서 어떤 낚시를 하는 배들이 어떤 조황을 올렸는가?’이다. 초기에는 참여 선사가 외부 공개를 허용한 조황만 제공한다.

## 2. 문제와 목표

### 2.1 해결할 문제

- 선사별 밴드에 정보가 분산되어 최근 조황을 비교하기 어렵다.
- 글마다 출조일, 어종, 낚시 방식, 수량 표기가 달라 검색하기 어렵다.
- 실제 조황과 예약 모집·광고·공지 글이 섞여 있다.
- 게시일과 실제 출조일이 달라 오래된 조황을 최근 조황으로 오인할 수 있다.
- 같은 조황의 반복 게시, 사진만 있는 글, 다수 어종 해시태그 때문에 분류 오류가 발생할 수 있다.

### 2.2 MVP 목표

1. 참여 선사의 최근 조황을 하나의 모바일 화면에서 탐색한다.
2. 어종·낚시 방식·항구·출조일로 결과를 좁힌다.
3. 원문 사실과 자동 추출·요약 결과를 구분한다.
4. 게시물의 출처와 마지막 확인 시각을 보여준다.
5. 관심 선사를 저장하고 해당 선사의 새 조황을 모아 본다.

### 2.3 초기 범위

| 항목 | 범위 |
|---|---|
| 지역 | 제주도 출항 선박 |
| 이용 환경 | iPhone·안드로이드의 모바일 브라우저 우선, 태블릿·PC 대응 |
| 출처 | 참여 선사의 네이버 밴드 |
| 핵심 대상 | 한치·갈치·참돔 조황. 나머지는 기타 어종으로 보존 |
| 방식 | 이카메탈·오모리그·외줄·텐빈·텐야·타이라바 등을 별도 분류 |
| 예약 | 선사의 기존 예약 페이지 또는 연락처로 연결 |
| 수집 대상 | 허용한 밴드 안에서 공개 대상 작성자·게시물로 승인된 조황 |

‘한치’는 어종, ‘타이라바’는 낚시 방식이다. 두 값을 같은 단일 분류에 섞지 않는다. 한 게시물에는 복수 어종·방식을 연결할 수 있다.

## 3. 사용자와 이용 시나리오

### 3.1 사용자

- 낚시 관광객: 제주 방문 전 최근 어종별 조황과 선사를 탐색한다.
- 제주 거주 낚시인: 가까운 항구와 관심 선사의 최근 소식을 확인한다.
- 선사 운영자: 기존 밴드 조황을 활용해 추가 작성 부담 없이 노출을 늘린다.
- 서비스 관리자: 참여 선사, 게시 허용 범위, 분류 오류, 연동 상태를 관리한다.

### 3.2 대표 시나리오

1. 이용자가 ‘갈치’를 선택하고 기간을 ‘최근 7일’로 설정한다.
2. 낚시 방식을 ‘텐빈’, 출항 항구를 원하는 항구로 좁힌다.
3. 카드에서 실제 출조일, 선박명, 조황 요약과 사진을 확인한다.
4. 상세 화면에서 원문 근거와 수량의 기준을 확인한다.
5. 관심 선사로 저장하거나 밴드 원문·예약 채널로 이동한다.

사진만 있고 출조일이나 조과 수치가 불명확한 글은 해당 값을 ‘미확인’으로 표시한다. 게시글이 없는 날을 ‘조황 나쁨’이나 ‘출항 없음’으로 처리하지 않는다.

## 4. 공식 BAND API 확인 사항

확인일: 2026-10-23. 아래는 문서 확인 결과이며, 실제 계정으로 호출한 검증 결과는 아니다.

| 기능 | 공식 문서상 제공 내용 | 활용 |
|---|---|---|
| 서비스 등록·인증 | 앱 등록, 계정 연결 또는 OAuth를 통한 접근 토큰 발급 | 운영자 연동 및 선사 계정 연결 |
| 가입 밴드 조회 | `GET https://openapi.band.us/v2.1/bands` | 연결 계정의 대상 밴드 선택 |
| 게시글 목록 조회 | `GET https://openapi.band.us/v2/band/posts` | 본문·작성자·게시 시각·사진 정보 수집 |
| 개별 글 조회 | `GET https://openapi.band.us/v2.1/band/post` | 상세 재확인 |
| 다음 페이지 조회 | 응답의 `paging.next_params` 이용 | 초기 적재와 후속 조회 |

게시글 목록에는 사용자 접근 토큰, band_key, locale가 필요하며, 공식 문서는 최종 수정일 순으로 목록을 반환한다고 설명한다. created_at은 게시 시각이므로 실제 출조일은 본문 등에서 별도로 식별한다. 문서에 없는 수정 시각 필드를 존재한다고 가정하지 않는다.

### 4.1 인증·공개 원칙

- 조회는 인증 계정이 접근할 수 있는 범위에서 수행한다.
- 계정 연결과 밴드 가입은 외부 재게시 동의와 별도로 관리한다.
- 선사가 권리를 확보한 본문·사진의 외부 공개, 요약·분류 처리 범위를 확인한다.
- 일반 회원의 게시글·댓글·프로필은 기본 공개 대상에서 제외한다.
- 선사 관리자라는 역할만으로 제3자 콘텐츠의 이용 권한까지 확보한 것으로 판단하지 않는다.
- 초기 검증은 운영자 본인 토큰으로 가능하다. 선사별 자가 연결 운영은 OAuth 흐름과 서비스 등록 조건을 검증한 후 적용한다.
- 접근 토큰과 클라이언트 시크릿은 서버에서 보관한다. 브라우저 코드·응답·로그·Git 저장소에 노출하지 않는다.

### 4.2 개발 전 실제 검증할 사항

1. 신규 앱 등록 및 필요한 읽기 권한 발급 가능 여부
2. 참여 밴드의 공개 형태와 계정 역할에 따른 조회 범위
3. 실제 사진 URL의 표시 가능 범위와 유효성
4. 게시글 원문 URL 확보 방식과 모바일 앱·웹 이동 동작
5. 호출 한도, 반복 호출 정책, 인증 만료·철회 동작
6. 게시글 수정·삭제·밴드 탈퇴 때의 응답과 동기화 방법
7. 저장·외부 공개·자동 분석에 적용되는 현행 플랫폼 조건

이 검증이 완료되기 전에는 모든 밴드 자동 수집, 실시간 갱신, 사진 영구 제공을 보장하지 않는다.

## 5. 화면 설계

### 5.1 홈 / 조황 피드

- 상단: 서비스명, 선박명·검색어 입력창
- 어종 선택: 전체 / 한치 / 갈치 / 참돔 / 기타
- 필터: 출조일, 낚시 방식, 출항 항구, 선사
- 기본 정렬: 확인된 출조일 최신순. 출조일 미확인은 별도 표시하고 게시일로 정렬
- 카드: 허용된 대표 사진, 선박명, 출항 항구, 출조일, 게시일, 어종, 방식, 짧은 요약, 출처
- 마지막 정상 동기화 시각과 갱신 지연 안내
- 하단 메뉴: 조황 / 선사 / 관심

필터는 모바일 하단 시트에서 조정하며, 적용한 조건과 초기화 버튼을 결과 상단에 표시한다.

### 5.2 조황 상세

- 사진, 선박명·항구, 출조일·게시일
- 어종·방식, 조과 수치와 수량 기준
- 짧은 조황 요약과 ‘자동 요약’ 표시
- 해당 값을 뒷받침하는 허용된 원문 발췌 또는 근거 설명
- 원문에서 확인 / 선사 보기 / 예약 채널 / 전화 문의
- 정보 오류·삭제 요청

사진 이용이 허용되지 않은 글은 기본 이미지와 허용된 정보만 표시한다. 원문 열람에 밴드 가입이나 로그인이 필요할 수 있음을 링크 주변에 안내한다.

### 5.3 선사 목록·상세

- 선박명, 출항 항구, 주요 어종·방식, 확인된 연락처
- 최근 조황 목록
- 공식 밴드·예약 채널 링크
- 관심 선사 추가·해제
- 실제 출항 항구 변경 이력이 있으면 조황에 당시 항구를 보존

### 5.4 관심 선사

- 관심 선사별 최근 조황 모아 보기
- MVP는 로그인 없이 해당 브라우저에 관심 목록 저장
- 기기 간 동기화와 푸시 알림은 후속 기능

### 5.5 관리자 화면

- 선사·밴드 연결, 허용 작성자와 공개 범위 설정
- 동의 근거·날짜·철회 상태 기록
- 수집 상태, 오류, 마지막 성공 시각 확인
- 자동 분류 검토·수정, 중복 병합, 게시·숨김 처리
- 게시글·선사 단위 공개 중단과 삭제 요청 처리

## 6. 기능 요구사항과 수용 기준

| ID | 요구사항 | 우선순위 | 수용 기준 |
|---|---|---|---|
| FR-001 | 선사·밴드 등록 | Must | 선사와 밴드의 연결, 허용 작성자·동의 범위가 저장되고 미승인 출처는 공개되지 않는다. |
| FR-002 | BAND 인증 | Must | 정상 토큰으로 조회하며 만료·권한 철회 시 해당 연결을 중단하고 관리자에게 표시한다. |
| FR-003 | 게시글 동기화 | Must | 초기 조회·다음 페이지 조회·반복 동기화를 지원하고 동일 글이 중복 생성되지 않는다. |
| FR-004 | 게시물 유형 분류 | Must | 실제 조황·모집·공지·기상 취소·미확인을 구분하고 조황 피드에는 승인된 조황만 노출한다. |
| FR-005 | 어종·방식 추출 | Must | 복수 값을 지원하며 해시태그에만 나온 값은 본문 근거 없이 실제 조황으로 확정하지 않는다. |
| FR-006 | 날짜 분리 | Must | 출조일·게시일·수집일을 별도 관리하고 출조일 미확인을 표시한다. |
| FR-007 | 조황 목록·필터 | Must | 어종·방식·항구·출조일·선사 필터를 함께 적용하고 뒤로 가기 때 조건과 위치를 복원한다. |
| FR-008 | 상세·원문 연결 | Must | 출처·날짜·허용 사진·본문 정보를 표시하고 검증된 원문 링크로 이동한다. |
| FR-009 | 선사 탐색·연락 | Must | 선사별 조황과 확인된 예약·문의 채널을 제공한다. 실시간 잔여석으로 오인되는 표현을 쓰지 않는다. |
| FR-010 | 관심 선사 | Should | 브라우저를 다시 열어도 관심 선사가 유지되며 추가·해제가 가능하다. |
| FR-011 | 중복 처리 | Must | 같은 원문 ID의 반복 수집은 갱신 처리하고 별도 글의 중복 의심은 관리자 검토로 연결한다. |
| FR-012 | 수정·삭제·철회 대응 | Must | 검증된 삭제·공개 철회는 노출을 중단하며 권한 오류는 삭제로 오판하지 않는다. |
| FR-013 | 요약·관리자 교정 | Should | 요약 실패 시 허용된 발췌·기본 정보로 대체하고 수동 교정은 후속 동기화에 덮어쓰지 않는다. |
| FR-014 | 빈 결과·오류 안내 | Must | 결과 없음·초기 적재 중·연결 오류·갱신 지연 상태를 구분한다. |

## 7. 데이터 정의

### 7.1 주요 데이터

| 개체 | 주요 항목 |
|---|---|
| 선사·선박 | 내부 ID, 선사명, 선박명, 기본 출항 항구, 공식 연락처, 예약 URL |
| 출처 연결 | 밴드 식별자, 선사 연결, 인증 참조, 허용 작성자, 동의 범위·시각, 활성 상태 |
| 원문 | 밴드 식별자, 게시글 식별자, 본문, 게시 시각, 사진 메타데이터, 검증된 원문 URL, 내용 해시 |
| 조황 | 출조일, 출조 당시 항구, 어종 배열, 방식 배열, 게시물 유형, 요약, 공개 상태 |
| 조과 주장 | 어종, 수량·단위, 개인·선박 전체·개인 최고·불명 기준, 근거 문구, 추출 상태 |
| 운영 이력 | 최초 수집, 마지막 확인, 변경 감지, 수동 교정, 비공개·삭제·철회 시각 |

원문 데이터와 외부 공개용 데이터를 분리한다. 댓글과 회원 프로필은 조황 서비스에 필요하지 않으므로 수집·공개 범위에서 기본 제외한다.

### 7.2 추출 규칙

- 수량: ‘100수’는 원문 주장으로 저장하고 검증된 실측값으로 표시하지 않는다.
- 기준: 개인 최고와 배 전체 수량을 서로 비교 가능한 동일 지표로 취급하지 않는다.
- 항구: 출항 항구와 실제 낚시 해역을 구분한다. 항구 위치를 조황 발생 지점으로 표시하지 않는다.
- 날짜: 제목·본문의 명시 날짜를 우선한다. ‘어제’처럼 상대 표현만 있으면 게시 시각을 기준으로 해석하고 추정 여부를 기록한다.
- 사진: 사진만 보고 어획량을 추정하거나 합산하지 않는다.
- 태그: 범용 홍보 해시태그보다 해당 출조를 설명하는 제목·본문을 우선한다.
- 신뢰도: 추출 결과의 확실성은 조황의 진실성이나 어획 가능성을 뜻하지 않는다.
- 계절: 고정 월별 시즌표로 실제 조황을 제외하지 않는다. 계절별 탐색은 축적된 관측과 선사 안내를 근거로 후속 도입한다.

## 8. 수집·처리 설계

처리 순서는 ‘승인된 출처 선택 → 서버에서 API 조회 → 원문 갱신·중복 확인 → 유형·날짜·어종·방식 추출 → 공개 조건 확인 → 피드 제공’이다.

### 8.1 동기화 추천 기본값

- 참여 선사 5~10곳으로 시작한다.
- 최초 적재는 최근 30일을 목표로 하되 페이지 조회량·호출 한도에 맞춰 조정한다.
- 갱신 간격은 60분을 가정하며 실제 API 한도와 비용 확인 후 확정한다.
- 이용자 화면 새로고침은 저장된 결과를 조회한다. 이용자마다 BAND API를 직접 호출하지 않는다.
- 수정일 정렬을 고려해 최근 페이지를 겹쳐 확인한다. 수정 시각 필드가 없으면 본문·사진 메타데이터 해시로 변경을 감지한다.
- 신규 글 수와 페이지 크기에 따라 호출 횟수가 달라지므로 ‘밴드당 한 번 호출로 모든 글 확보’를 가정하지 않는다.
- 오류 시 반복 호출 간격을 늘리고 연결별 마지막 성공 상태를 보존한다.

### 8.2 삭제와 접근 실패

- 최근 공개 글은 주기적으로 원문 상태를 재확인한다. 재확인 주기는 API 한도 검증 후 확정한다.
- 원문 삭제가 명확히 확인되면 피드·상세·관련 사진의 공개를 중단한다.
- 인증 만료나 일시 장애는 원문 삭제와 구분한다. 오류가 계속되어 허용 상태를 확인할 수 없는 자료는 보수적으로 숨긴다.
- 선사의 공개 동의 철회 시 해당 연결의 신규 수집을 중단하고 기존 공개 자료를 숨긴다.
- 원문·사진·캐시·백업의 삭제 범위와 보존 기간은 공개 운영 전에 플랫폼 조건과 동의 범위에 맞춰 정한다.

### 8.3 AI 적용

- 초기에는 규칙으로 날짜·어종·방식을 추출하고 불확실한 결과를 검토한다.
- AI 요약·보조 추출은 선택 기능이다. 이용 가능한 API와 처리 동의·예산이 확정되면 활성화한다.
- 비용을 줄이기 위해 원문이 바뀐 경우에만 재처리하고 결과를 저장한다.
- 외부 글은 분석 대상 데이터로 취급한다. 글에 포함된 명령·링크를 실행하지 않는다.
- AI 실패나 한도 소진으로 조황 목록 전체가 중단되지 않도록 기본 정보 표시를 유지한다.

## 9. 비기능 요구사항

- 시간: 저장 시 표준 시각을 사용하고 사용자 화면은 한국 시간으로 표시한다.
- 사용성: 모바일 세로 화면에서 가로 스크롤 없이 탐색하며 필터·전화·원문 버튼을 쉽게 누를 수 있게 한다.
- 접근성: 텍스트 대비, 버튼 이름, 대체 텍스트를 제공하고 색상만으로 상태를 표현하지 않는다.
- 성능: 대표 사진 지연 로딩·크기 최적화, 목록 페이지 분할, 저장된 응답 활용을 적용한다.
- 보안: 관리자 인증, 최소 권한, 서버 비밀정보 보관, 토큰 로그 마스킹을 적용한다.
- 운영: 출처별 최근 성공·실패, 공개 조황 수, 분류 검토 대기 수를 확인할 수 있다.
- 비용: 월 예산은 미정이다. API 이용 조건·호스팅·DB·이미지·AI 비용을 확인한 후 상한과 중단 정책을 확정한다. 월 0원을 보장하지 않는다.

## 10. MVP에서 제외하는 기능

- 네이버 밴드 외 SNS·선상24 자동 연동
- 자체 예약·결제·실시간 잔여석 집계
- 조과가 좋은 배 순위, 어획 성공 확률·출항 가능 여부 자동 판정
- 사진 기반 어종·어획량 자동 확정
- 일반 회원의 비공개 글·댓글 공개
- 실시간 바다 날씨·물때·수온 통합
- 회원 계정, 기기 간 관심 목록 동기화, 푸시 알림

후속 후보는 물때·해양 기상, 관심 어종 알림, 과거 시즌별 조황 탐색, 선사 직접 등록이다. 날씨와 조황을 연결하더라도 표본 편향과 미게시 출조를 고려해야 한다.

## 11. 검증 및 완료 기준

### 11.1 1차: 한 개 밴드 기술 검증

1. 협조 선사와 공개 대상 작성자·사진·본문 범위를 확인한다.
2. 앱 등록·계정 연결 후 대상 밴드 목록을 조회한다.
3. 최근 게시글과 사진 메타데이터, 다음 페이지를 확인한다.
4. 게시일과 실제 출조일을 구분하고 원문 이동을 확인한다.
5. 통제된 테스트 글로 수정·삭제·권한 철회 동작을 확인한다.
6. 호출 한도·사진 이용·저장·공개 조건을 정리한다.

완료 조건: 게시글을 가져오는 것뿐 아니라 승인된 자료를 공개하고 수정·철회를 반영하는 경로까지 확인한다.

### 11.2 2차: 데이터·화면 검증

- 선사 5~10곳을 목표로 확대한다.
- 실제 조황·모집·혼합 글·사진 전용 글·상대 날짜·중복 글이 포함된 표본을 선정한다.
- 게시물 유형, 어종·방식, 출조일, 수량 기준을 사람이 판독한 결과와 비교한다.
- 추천 목표: 명시 정보가 있는 표본의 핵심 추출 정확도 95% 이상. 항목별 분모·미확인·오류 수를 별도 보고하며 운영 전 기준을 확정한다.
- 오분류는 관리자 교정 후 재동기화해도 유지되는지 확인한다.
- 필터 조합, 뒤로 가기, 관심 저장, 원문 로그인 필요, 결과 없음·갱신 지연 화면을 확인한다.

### 11.3 공개 전 필수 조건

- 미승인 출처·작성자의 콘텐츠가 공개되지 않는다.
- 토큰·회원 개인정보가 브라우저나 로그에 노출되지 않는다.
- 사진·본문의 허용 범위와 삭제 요청 경로가 정해져 있다.
- 실제 조황과 모집 글, 출조일과 게시일을 구분한다.
- API 장애·철회 시 노출 중단과 운영자 대응을 확인했다.
- 비용 상한과 동기화 주기가 정해져 있다.

## 12. 개발 단계

| 단계 | 작업 | 산출물 |
|---|---|---|
| 1 | BAND 실제 연동·이용 범위 검증 | 조회 예제, 응답 필드표, 조건·제약 목록 |
| 2 | 데이터·분류 설계 | 선사·출처·원문·조황 구조, 추출 규칙, 검토 표본 |
| 3 | 모바일 화면 구현 | 피드·필터·상세·선사·관심 화면 |

| 5 | 참여 선사 시범 운영 | 실제 조황 품질 검증, 갱신·비용 측정, 공개 준비 |

기술 스택과 배포 환경은 1단계 검증 후 확정한다. 필수 구성 요소는 모바일 프런트엔드, 인증·수집 서버, 일정 실행 기능, 조황 저장소, 최소 관리자 화면이다.
